Review of SoulcloudJS and the ESP-IDF Soulcloud component, 2026-09-20.

Scope: client protocol decoding, command dispatch, MQTT handoff, logging, OTA and teardown; server command delivery, result persistence, OTA identity, log decoding/cache, and a structural inspection of the plugin manager. This is a focused code review, not an exhaustive audit of every UI/plugin path or a hardware soak test.

Six confirmed issues were fixed with local changes. No new service, dependency, database schema, or wire field was introduced.

1. **High — command argument keys referenced dead stack memory. Fixed.**
   `components/soulcloud/src/protocol.cpp`, `decode_command_exec`: argument keys were pointed at `tmp.key_storage`, followed by `*out = tmp`. The copy preserved the pointers into the temporary. A handler reading a key after decoding could see corrupted data or perform an invalid access. AddressSanitizer reproduced a stack-use-after-return in the existing golden-fixture test. The decoder now rebinds keys to the output's storage. A regression assertion checks ownership directly.

2. **High — teardown leaked capability-allocated buffers and the core task. Fixed.**
   `components/soulcloud/src/soulcloud.cpp`, `client_impl::destroy`, and `src/logs.cpp`, initialization error paths and `deinit`: `xRingbufferCreateWithCaps` allocations were passed to `vRingbufferDelete`, and `xTaskCreateWithCaps` to `vTaskDelete`. The installed ESP-IDF implementation creates these through static-allocation APIs; ordinary deletion does not free their backing allocations. At default sizes, successful init/deinit leaked two 16 KiB ring buffers and a 16 KiB core stack, plus metadata/TCB. Cleanup now uses the matching `WithCaps` APIs. The ordinary OTA task still correctly uses ordinary task deletion. Evidence: installed `esp_ringbuf/ringbuf.c` and `freertos/esp_additions/idf_additions.c`, plus their API contracts. Firmware compilation passed; repeated lifecycle heap measurement on hardware remains unperformed.

3. **High — command and OTA results could be acknowledged and then lost. Fixed for uplink persistence.**
   [dispatch.ts](../../packages/broker/src/mqtt/dispatch.ts): only `/event` used the persistence-before-acknowledgement path. The installed Aedes QoS1 implementation sends PUBACK before the ordinary publish handler. A database outage, queue overload, or rate-limit drop could therefore discard an already acknowledged command result, leaving its command and later commands blocked. Results now use the existing durable admission path; database failures and temporary admission failures reject acknowledgement. Invalid or unmatched results remain deliberately ignored. Six regression tests failed before the fix and passed afterward, covering command/OTA persistence ordering, errors, duplicate dispatch avoidance, and rate limiting. This does not solve the separate downlink restart problem below.

4. **Medium — throttled full log batches could remain unsent indefinitely. Fixed.**
   `components/soulcloud/src/logs.cpp`, `next_deadline_us` and `batch_flush_due`: after the first full-batch flush failed for lack of rate credit, the later drain checked only timeout/watermark. With the optional timeout disabled, an otherwise quiet queue never retried the flush. Count-full batches could repeatedly wake without flushing; byte-full batches could lack a retry deadline entirely. Both scheduling and flushing now recognize both fullness conditions. A host harness compiled the actual scheduling methods before and after the change: the original failed count-full and byte-full cases; the patched methods passed without new packets or a timer.

5. **Medium — the log dictionary cache did not enforce its declared entry limit. Fixed.**
   [decode.ts](../../packages/core/src/logging/decode.ts): crossing 200 entries only evicted expired entries. A burst of fresh artifact dictionaries could grow beyond that limit. After expired-entry eviction, it now evicts oldest insertions until the existing limit is satisfied. A regression test inserts 201 fresh artifacts and verifies eviction and reloading. This bounds dictionary count, not the total bytes of arbitrarily large dictionaries.

6. **High — unknown MessagePack fields could recurse through the embedded stack. Fixed.**
   `components/soulcloud/src/protocol.cpp`, `msgpack_reader::skip_value`: the bundled streaming `mpack_discard` recursively skips arrays/maps without consulting `MPACK_MAX_DEPTH`. Thousands of nested singleton arrays fit in a legal inbound packet, despite the nominal depth setting of 32. Skipping now enforces the existing depth setting, using MPack's scalar discard only for noncontainers. Host tests cover a deeply nested value and normal nested map/array compatibility. No heap allocation was added.

Three cross-component issues remain open. They need an explicit contract/recovery change rather than an incidental patch:

7. **High — broker restart can strand accepted downlink commands.**
   [broker.ts](../../packages/broker/src/mqtt/broker.ts:135) creates Aedes with its default memory persistence. [acknowledge.ts](../../packages/core/src/queue/acknowledge.ts) moves commands to `broker_accepted`; [lease.ts](../../packages/core/src/queue/lease.ts) only leases queued or expired leased rows, while an earlier accepted row blocks later commands. If the broker dies after recording acceptance but before delivery, MQTT's in-memory delivery state disappears. With the default null delivery deadline, the row has no recovery path. The current README claim that a crashed process cannot lose work is too strong. Do not blindly requeue all accepted commands: the client dedupe cache is volatile and only eight entries, so that can repeat side effects. Define retry/uncertain-outcome semantics and dedupe lifetime together, or introduce durable broker persistence with a carefully tested transition policy.

8. **High — API-valid command sizes exceed client capabilities.**
   [command.ts](../../packages/core/src/protocol/command.ts) has no client-sized command/argument limits. The client accepts at most eight arguments, 39-byte argument keys, 255-byte command names, and normally 4096-byte complete payloads. Decodable field-limit violations produce an error result, but an oversized complete payload is dropped in `mqtt_bridge.cpp`/`soulcloud.cpp` before that response path. QoS1 does not make an application drop retryable after transport acknowledgement. For example, a command with a 5000-byte string argument is API-valid but cannot complete on the default client, and can block its queue. The smallest follow-up is an explicit shared device command profile validated before enqueue; account for UTF-8 bytes and the complete encoded envelope. A global hardcoded 4096-byte rule would change the contract for other clients and still fail clients configured with smaller buffers, so it was not silently added.

9. **High — bin-only OTA completion uses a different identity from this client.**
   `components/soulcloud/src/soulcloud.cpp`, `build_stat`, reports `esp_app_get_elf_sha256`. [deploy.ts](../../packages/core/src/ota/deploy.ts:617) compares that value with the full uploaded BIN SHA-256 when the release has no ELF artifact. Those are different hashes. A successful bin-only update can remain `installed` instead of becoming `completed`, blocking a rollout. Keep firmware/build identity separate from download-integrity identity. For this ESP-IDF client, a follow-up can validate/extract the embedded application ELF hash from the BIN at release creation and persist it, retaining compatibility with existing releases. That requires a release-data migration and binary-format tests; it was not replaced with a guessed success transition.

Design and RAM observations, distinct from correctness bugs:

- **The persistent OTA worker is the clearest questionable optimization.** `src/ota.hpp` reserves a 10,240-byte task stack from initialization until teardown, and `ota.cpp` keeps a SHA context allocated, explicitly to avoid allocations on OTA retries. OTA is normally infrequent. Creating/freeing one bounded worker per update would trade rare allocation activity for approximately 10 KiB of idle RAM, but worker lifetime and cancellation must remain correct. No lifecycle redesign was mixed into the fixes.
- **Fixed buffers deserve a measured budget, not blanket removal.** The command result cache reserves over 8 KiB; the log batch buffer reserves 4,103 bytes even with batching disabled by default. Default core stack, ring buffers, fragmentation storage, OTA stack, log assembly/batch storage, result cache, and MQTT input/output buffers total roughly 90 KiB before task metadata, MQTT stack, TLS, and other application allocations. Some buffers move to PSRAM where available. Make optional features/configurable capacities explicit when RAM measurements justify it; retain bounded storage on frequent paths.
- **Normal command/log parsing is already reasonably allocation-conscious.** Borrowed payload values, fixed output buffers, and ring-buffer handoff are useful choices. The obvious issue is permanent RAM reservation and teardown leakage, not a demonstrated malloc/free storm in those paths. MPack's hot path did not need replacement.
- **The plugin-manager split retains substantial shared coupling.** `packages/plugin-manager/src/manager.ts` forwards into `manager/*` modules which receive the whole mutable manager; many files repeat broad imports. That separation improves file size more than encapsulation. Narrow dependencies when changing a subsystem, and remove unused imports opportunistically. A new abstraction framework or rewriting the plugin architecture is not justified by this review.
- **API/broker separation and a database-backed command outbox are reasonable.** The concrete problems are transition/recovery gaps, not evidence that these components should be collapsed or replaced.

Validation of the final changes:

- Bun version verified as **1.4.2**; complete backend suite rerun: **868 passed, 0 failed** across 83 files.
- Frontend suite on Bun 1.4.2: **228 passed, 0 failed** across 36 files; production build passed.
- Backend TypeScript check passed; frontend build includes its TypeScript check.
- Client host protocol suite: **130 successful checks**, with AddressSanitizer and stack-use-after-return detection. LeakSanitizer was disabled because the execution sandbox's tracing prevents it from operating; AddressSanitizer memory-access checking remained enabled.
- Count/byte-full log scheduling reproduced failing before and passing after the fix in a host harness.
- Final ESP-IDF ESP32-S3 firmware build passed. No flashing, hardware OTA cycle, or hardware lifecycle soak was performed.
- Database tests used a dedicated review database, first verified absent and then created by this review. Existing development/test databases were not reset. The disposable `soulcloud_review_20260920` database remains available for inspection.
- Fixes were committed and pushed by topic to each repository's `origin/master`. The demo client submodule reference was updated separately. Its pre-existing `dependencies.lock` and `.clang-format` changes were left alone.

Additional performance change requested after the review:

- `packages/core/src/protocol/structure.ts`: read marker/length bytes directly instead of allocating a one-byte `Uint8Array` view for each. The bounds-error path still uses the existing checked reader, preserving error text and behavior. No API or data-format change.
- On Bun 1.4.2, the real client command fixture took a median **86.02 ms before / 61.18 ms after** per 100,000 structural validations, approximately **29% less time**. Nine alternating before/after measurements followed 10,000 warm-up iterations. This measures the structural validator only, not end-to-end broker throughput.
- Differential validation of 20,000 deterministic byte buffers produced identical accept/reject outcomes and error names/messages. Permanent tests cover truncated markers/length prefixes and nonzero-offset input views. The complete backend suite was rerun after this change: **868 passed**, with TypeScript checking also passing. The client sanitizer suite and log-scheduling reproducer were rerun before topic commits.
