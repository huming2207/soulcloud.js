# Log 容器协议（Soulcloud 日志上行打包协议）

> 协议以英文版 docs/en/protocol-log-packaging.md 为准（authoritative），中文版仅供参考。

**日期**：2026-08-09 · **状态**：已定稿的设计，实现进行中（平台 + 固件）· **读者**：固件开发者

本文档规定日志数据如何通过 MQTT `log` 话题
（`soulcloud/v1/devices/{device_uid}/log`，QoS 1）从设备传送到 Soulcloud
平台。它用带版本号的**分派容器**取代了原先"仅原始数据包"的契约：首字节选择
负载格式，因此将来可以增加新格式，而无需再次破坏性变更。

## 1. 容器分派（Container dispatch）

发布到 `log` 话题的每个负载都以一个类型字节开头：

| 首字节 | 格式 | 状态 |
| --- | --- | --- |
| `0x9a` | 原始 on9log 数据包（on9log 魔数；单个数据包，与之前相同） | 支持 |
| `0x01` | MessagePack 聚合数组（一次发布携带多个 on9log 数据包） | 支持 |
| 其他任何值 | 保留给未来格式（原始文本、JSON 等） | 禁止发送 |

## 2. 类型 `0x9a` — 原始 on9log 数据包

负载恰好是一个 on9log 数据包，按 on9log 组件的定义：

```
18 字节小端头部：
  uint8  magic       = 0x9a
  uint8  type_level  （高半字节：数据包类型，低半字节：级别）
  uint16 seq         （自然回绕）
  uint32 time_ms     （自启动以来的毫秒数，自然回绕）
  uint32 tag_id      （标签字符串的 ELF 地址）
  uint32 fmt_id      （格式字符串的 ELF 地址）
  uint16 payload_len （0xffff = 流式；否则为负载长度）
```

其后是数据包负载（LOG 参数、DROPPED 计数器、TIME_SYNC 字段、BUFFER 块、
或不透明的 BOOT 字节）。单个数据包请使用此形式发送——没有理由把单个数据包
包进容器。

## 3. 类型 `0x01` — MessagePack 聚合数组

负载是一个 MessagePack **二进制块数组**；每个元素是一个完整的 on9log
数据包（`0x9a` 形式，见 §2）。

- 数组头：`fixarray`（`0x90 | n`，n ≤ 15）或 `array16`
  （`0xdc` + 2 字节大端计数）用于 16–4096 个元素。（元素数 ≤ 4096 的
  `array32` 根也接受。）
- 每个元素：`bin8`（`0xc4` + 1 字节长度，块 ≤ 255 字节）或 `bin16`
  （`0xc5` + 2 字节大端长度，块 ≤ 65535 字节）。二进制长度即元素的字节
  长度，因此元素是自定界的。
- 元素不得为空，且必须以 on9log 魔数 `0x9a` 开头。
- 平台丢弃并计数畸形元素（类型错误、为空、魔数错误、on9log 内容被截断），
  容器其余部分照常处理——单个坏元素永远不会连累它的兄弟元素。
- 每个容器的元素数上限为 **4096**。消息代理的传输层保留 256 KB 的提前拒绝
  上限，但设备上行**具有约束力的**单次发布上限是可配置的
  `UPLINK_MAX_PACKET_BYTES`（默认 64 KB），由分派层强制执行——请按这个值
  来估算容器大小，而不是按 256 KB。
- 限流按**发布次数**计数，不按元素计数：一个容器只消耗一个限流令牌，却可
  携带多达 4096 个数据包。这是有意为之（合并本来就是目的），而 64 KB 的
  发布上限限制了放大倍数。
- 每个元素都是独立的 on9log 数据包，带有**自己的 `seq` 和 `time_ms`**——
  容器本身不添加任何时间戳或序列号。

### 3.1 字节级示例

三个 on9log LOG 数据包合并进一个 `0x01` 容器：

```
数据包 A — LOG，级别 INFO，无参数（20 字节）：
  9a 03 01 00 64 00 00 00 00 10 00 00 00 20 00 00 02 00 01 00
  ─┬─ ─┬─ ───┬─── ─────┬───── ────┬──── ────┬──── ──┬── ─┬─ ─┬─
   │   │      │         │          │         │       │   │   └── arg_types[0] = 0x00（NONE 哨兵）
   │   │      │         │          │         │       │   └── arg_count = 0x01（NONE 类型参数；
   │   │      │         │          │         │       │       零参数 LOG 仍必须携带哨兵类型字节 —
   │   │      │         │          │         │       │       仅 payload 0x00 会被严格解析器拒绝）
   │   │      │         │          │         │       └── payload_len = 0x0002
   │   │      │         │          │         └── fmt_id = 0x00002000
   │   │      │         │          └── tag_id = 0x00001000
   │   │      │         └── time_ms = 100 (0x64, u32 小端)
   │   │      └── seq = 1 (u16 小端)
   │   └── type_level = 0x03（type 0 LOG << 4 | level 3 INFO）
   └── magic 0x9a

数据包 B — LOG，一个 32 位参数 = 42（24 字节）：
  9a 03 02 00 65 00 00 00 00 10 00 00 00 20 00 00 06 00 01 01 2a 00 00 00
  ─┬─ ─┬─ ───┬─── ─────┬───── ────┬──── ────┬──── ──┬── ─┬─ ─┬─ ────┬────
   │   │      │         │          │         │       │   │   │      └── 参数值 = 42 (0x2a, u32 小端)
   │   │      │         │          │         │       │   │   └── arg_types[0] = 0x01（32BITS）
   │   │      │         │          │         │       │   └── arg_count = 0x01
   │   │      │         │          │         │       └── payload_len = 0x0006
   │   │      │         │          │         └── fmt_id = 0x00002000
   │   │      │         │          └── tag_id = 0x00001000
   │   │      │         └── time_ms = 101 (0x65)
   │   │      └── seq = 2
   │   └── type_level = 0x03（LOG, INFO）
   └── magic 0x9a
   │   │      │         │          │         └── fmt_id = 0x00002000
   │   │      │         │          └── tag_id = 0x00001000
   │   │      │         └── time_ms = 101 (0x65)
   │   │      └── seq = 2
   │   └── type_level = 0x03（LOG, INFO）
   └── magic 0x9a

数据包 C — LOG，一个动态字符串 "ok"（26 字节）：

  ─┬─ ─┬─ ───┬─── ─────┬───── ────┬──── ────┬──── ──┬── ─┬─ ─┬─ ────┬──── ────┬───

   │   │      │         │          │         │       │   │   └── arg_types[0] = 0x04（DYNAMIC_STRING）
   │   │      │         │          │         │       │   └── arg_count = 0x01
   │   │      │         │          │         │       └── payload_len = 0x0008
   │   │      │         │          │         └── fmt_id = 0x00002000
   │   │      │         │          └── tag_id = 0x00001000
   │   │      │         └── time_ms = 102 (0x66)
```

## 4. 固件实现指南

- **编码器**：使用成熟的 MessagePack 编码器——C/C++ 用 `msgpack-c`
  （`msgpack_pack_array`、`msgpack_pack_bin`），Rust 用 `rmp-serde` 或
  `rmp`。本话题只需要 `array` 和 `bin` 两种；MessagePack 规范中的其他
  内容一概不用。
- **何时合并——背压触发，而不是固定定时器。** 实时投递是一项特性：平台
  在日志到达时实时流式推送到 Web 控制台。默认继续逐条发布原始数据包
  （类型 `0x9a`），让日志行立即出现。只有当设备的出站队列积压时
  （建议阈值：**积压超过 16 个数据包**）才把队列排空成一个 `0x01` 容器。
  固定 10 秒窗口是错误形态：它给常见情况增加延迟，在流量稀疏时又一无所获。
- **一次发布，一个容器**：容器与原始数据包完全一样，作为 `log` 话题上的
  单次 MQTT PUBLISH（QoS 1）发送。QoS 和话题语义不变。
- **有界内存**：当容器负载达到约 4 KB 或 128 个元素时（以先到者为准）立即
  刷新，以免异常突发把队列卡在一个巨型数据包后面（平台的 256 KB 上限还很
  远；留出宽裕余量）。
- **合并是尽力而为**：如果设备带着已满的队列崩溃，缓冲的日志将丢失。
  在日志最要紧的时候（故障诊断）绝不要合并——那恰恰是队列填满的时候，
  所以宁可及时刷新不完整的容器，也不要等待凑满一个。
- **元素有效性**：每个元素必须是一个完整的 on9log 数据包，以 `0x9a` 开头。
  绝不要把数据包拆到多个元素或容器中；`payload_len` 不是 `0xffff` 的数据包
  必须整体发送。

## 5. 平台侧处理（供参考）

- 消息代理按首字节分派，拆分 `0x01` 容器，并让每个元素走与类型 `0x9a`
  **完全相同的单数据包路径**进行摄取：校验 → 每个数据包在 `raw_log_events`
  中一行 → 为日志流发送实时通知。畸形元素被丢弃并计数，绝不会让容器或连接
  致命。
- 因为每个元素保留自己的 on9log `seq` 和 `time_ms`，解码（ELF 字典查找 +
  格式渲染）、序列号间隙检测和实时日志流都原样工作。容器格式对每个下游
  消费者都是不可见的。
